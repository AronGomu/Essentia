Measured on this machine, tonight

  • npm run dev = 109 s before Astro even starts. Split: cards:rebuild 0.3 s (already cached), build-content 107.4 s, astro build of all 152 pages 1.5 s. Astro is not the problem. Vite is not the problem.
  • All 107 s is image encoding. orchestrator.mjs does rm -rf public/generated on every run, then re-encodes 5 derivatives × 50 cards = 250 files (63 MB) from scratch, one card at a time, on 1 of your 16 cores.
  • Per card: 2.44 s. display.avif 1662 ms · thumb.avif 299 ms · print.png 315 ms · display.webp 114 ms · thumb.webp 46 ms. AVIF alone is 80 % of your whole build.
  • Scaling is linear and brutal: 2.1 s/card × 500 cards = 17 min per npm run dev.
  • The cache key already exists. packages.mjs computes renderHash, visualSourceHash and artworkHash per card and verifies them against render-provenance.json, right before it re-encodes everything anyway. public/generated/ is git-ignored, so a local cache is free.
  • Tour Guide's Burning Abyss link is hand-authored, not derived. content/identities.json gives it archetype: "burning-abyss", role: "support" with no linked: true — so it sits in the non-archetype section but relates to all 13 BA cards.
  • The second relation kind is derived from rule text and it is the one that explodes. related.mjs splits the oracle text on . ; — \n, keeps clauses carrying an action keyword, extracts constraints (subtype / quoted name / colour / supertype / MV) and scans every other card. Leviair matches 41 of 49 cards. Maxx "C" 21. Stealth Kragen 20.
  • Graph CPU is a non-issue; graph payload is. Benchmarked: 50 cards → 5 ms / 528 edges · 200 → 15 ms / 8 856 · 800 → 162 ms / 143 328 edges. Edges are quadratic; they land in catalog.ts and in every card page's HTML.
1. Image derivative caching — how do we stop re-encoding 250 files every run?

This single change is worth ~105 s of the 109 s, and it is what makes 500 cards survivable.

2. AVIF is 80 % of encode time — keep, cheapen, or drop?

Even with a warm cache, every new card pays 1.96 s for AVIF; a cold CI build pays it 500 times.

3. Should npm run dev generate fewer tiers than npm run build?

Determines whether local dev output is byte-identical to production or deliberately cheaper.

4. Derived “Interacts with” relations — how do we keep them from exploding?

Leviair already matches 41 of 49 cards; at 800 cards the same rule produces a page listing hundreds of cards and a multi-MB catalog.

5. Archetype backdrop — what element does it paint on?

You asked for the photo to stay inside the content area and off the header and rail; that boundary has to be one specific element.

6. How far does the theme removal go — and what about the 3 archetypes with no art?

Only burning-abyss and nekroz have a background file. Shaddoll, Spellbook and Non-archetype currently rely on the gradient you want removed.

7. Splitting blog / docs / cards — what is the actual target?

Your premise was that rebuilding everything is what costs you. Measured, Astro's share of that is 1.5 s; the 107 s is card images, which only the card side owns. The split may be solving an already-dead problem.

8. Docs grouping — where do groups come from, and who renames the files?

Today groups are hand-listed in content/reading-order.json; you want them to follow numbered folders on disk. Also, 8 docs currently sit loose at the root of docs/ (CONTEXT, DESIGN, RULES, KEYWORDS, GLOSSARY, MSE, RELEASES, SET_PROMOTIONS) and would need to move into a numbered folder.

9. Collapsible docs sections — default state and memory?

With one group per archetype the rail will have 8+ sections; what is open on arrival decides whether it feels navigable or empty.

10. /blog/ without a list — and which date format?

Two decisions in one place: what the blog landing route serves, and "numbers with slashes or dashes" is ambiguous between 08/08/2026 and 2026-08-08.

11. Removing the rail's Docs/Blog switch — mobile too?

The switch exists twice: in the desktop rail and in the mobile drawer. On a phone the header's utility nav collapses to short labels, so the drawer switch may be the only comfortable path between the two.
