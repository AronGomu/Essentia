Planned change — content-hash cache

Status: planned, not yet implemented. See docs/ADR/proposed/0038-content-hash-derivative-cache.md and ai-artifacts/PLAN_2026_08_13_feedback_batch_3.md tickets T1 and T2.

  • The rm -rf public/generated at build start is deleted; a manifest at public/generated/.derivative-manifest.json maps each output to a key over { sourceHash, tier, format, width, rev, options }.
  • A derivative is re-encoded only when its key changes or its file is missing. Files no longer claimed by any card are pruned explicitly.
  • AVIF drops from effort: 4 to effort: 2; dev and build keep emitting identical bytes.
  • npm run cache:verify rebuilds cold into a temp directory via GENERATED_PUBLIC_DIR and byte-compares against the cached tree; it runs in npm run ci.
  • Expected warm cost: ≈ 2.5 s for npm run dev, converging on the measured 0.66 s content floor.

What this pipeline deliberately does not do

  • No incremental catalog. Every run reparses every package. At 0.66 s that is not worth changing.
  • No parallel encoding. Encoding is serial on one core of sixteen. The cache removes the repeat cost; the cold cost stays linear, and CI pays it.
  • No split builds. Blog, docs and cards share one Astro app — see docs/ADR/proposed/0039-one-astro-app.md.
  • No request-time work. The site is fully static; "cache it" always means "compute it in the content build".
