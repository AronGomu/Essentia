02The judgement calls

Six entries were not simple confirmations of existing practice. These are the ones worth your disagreement, if any.

D-008 · conflict resolved

Print 2 copies, not 3/6

Deck-building doc demanded 3 copies per distinct card per deck and 6 when shared. The shipped tool and the real print manifest use a uniform 2. Chose the tool; the doc gets corrected in RST-101.

D-009 · newly decided

Copy limits closed

No rarity-based limits. Max 2 copies of a distinct card per deck, matching the Alpha_0.1 lists. Mythic starts at 1 copy only if a rarity system ever ships. Recorded as ADR 0014.

D-016 · scope boundary

Nothing gets locked

Alpha_0.1 stays open; the plan never runs lock. Locking is an irreversible publication boundary and playtest iteration is still live — excluded by decision, not left as a question.

D-004 · newly decided

Version arithmetic

advance carries X.Y into the next stage unchanged; a post-lock correction is Y + 1 in the same stage; open packages never bump. Ordering stays total without mtime.

D-018 · ownership split

Website work stays out

Deck pages, blog, historical grid belong to WEBSITE_V2_SPEC.md and TODO.md. The restructuring plan links them instead of re-deciding them.

D-021 · tooling pin

unittest, not pytest

CI runs python -m unittest discover -s tests and requirements-dev.lock is hash-pinned. pytest is not installed and must not be added casually.

04What happens if something new comes up

The plan carries a tie-break policy so a fresh ambiguity never becomes a blocking question. The agent resolves it, writes it down as a new D-### in the same commit, and keeps going.

# residual-ambiguity policy, in order
1. follow existing repo convention
2. pick the most reversible option
3. fail closed
4. record the choice as a new D-### in the plan  (same commit)
5. continue — never stop to ask

# actions the plan never performs
lock a package · deploy or publish · force-push
delete user-authored content · rewrite history
