1. How do card inputs fit the existing content/ convention?

Round 3 settled content/<setId>/<card-id>/. That answer was given without knowing content/context.md exists and documents a different rule: one dated folder per piece of content, YYYY-MM-DD-content-title/, filenames inside carrying no date. Fifty card folders is also a volume the existing flat convention was not designed for.

2. Where does the canonical slug function live?

Every input folder, output file and website URL is keyed by a slug produced by slugify() in website/scripts/content/shared.mjs. You settled that the pipeline reads cards_mse/ directly in Python. So the identifier is now minted in one language and consumed in two, and a one-character divergence writes files to a path the website will never look at.

3. Which model is pinned, and what happens when it fails?

Round 4 settled "a permissive English CTC model with torchaudio.functional.forced_align" rather than MMS_FA. Pinning which one, and deciding the failure behaviour, is the leaf. Since timing.json is committed, alignment runs once per card on your machine and never during a rebuild, so the failure path matters less than it would otherwise.

4. Which OFL sans gets vendored?

Round 3 settled "Open Sans or Lato" without choosing. All three candidates are SIL OFL and equally shippable, so this is taste with one objective tiebreaker: Aptos and Open Sans were drawn by the same designer, Steve Matteson.

5. How is a music track selected?

Round 3 settled a small pool, one track per set or archetype, selected deterministically, with a committed manifest naming track, source and licence. What keys the selection is the leaf. Note that three archetypes are live in the current catalog and two more exist only as drafts.
